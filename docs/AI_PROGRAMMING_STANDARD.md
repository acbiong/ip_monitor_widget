# AI 编程规范

适用于本项目中由 AI 辅助完成的代码、测试、文档和打包工作。

## 1. 工作原则

1. 先读取适用范围内的 `AGENTS.md`、开发规格书、接口文档和现有测试，再修改文件。
2. 优先修复根因，保持改动最小，不顺手重构无关功能，不删除用户已有配置兼容性。
3. 每个功能模块独立文件；跨模块协议必须在接口文档中说明输入、输出、错误和超时。
4. 代码注释和新增文档使用中文，变量和函数名称使用清晰的英文语义名称，禁止无意义单字母变量。
5. 不在代码中写入密钥、个人路径、临时调试输出或绕过 TLS/权限的方案。

## 2. 修改流程

- 修改前记录需求、影响模块和风险。
- 修改后先做语法/JSON 检查，再运行最小相关测试，最后运行回归和打包测试。
- 测试失败时保留真实失败信息，不通过修改断言或吞异常伪造成功。
- 更新 `docs/CHANGELOG.md`，并根据变更级别调整 `src/VERSION.json` 的基础版本。
- 构建只能通过 `src/packaging/build.sh` 触发；构建号由 `version_manager.py` 自动递增，不手工改写后缀。
- 每项功能修改先创建独立 Git 分支，完成后提交清晰的 commit；禁止把编译缓存、临时文件和发布输出强行加入版本库。
- 测试计划存放 `docs/test_plan/`，测试结果存放 `docs/test_reports/`，禁止混放。

## 3. 版本判断

- `MAJOR`：破坏配置、接口、运行方式或兼容边界。
- `MINOR`：向后兼容的新功能或可选能力。
- `PATCH`：向后兼容的缺陷修复、性能优化、文档和打包修复。
- 同一批次包含多个级别时取最高级别；只修改编译产物时不改变基础版本，只递增 build 后缀。

## 4. 交付要求

交付说明必须列出修改文件、验证命令、测试结果、产物路径、兼容边界和未验证事项。不得承诺“所有 deepin 都可运行”，除非有对应版本、架构和桌面环境的实际验证证据。
